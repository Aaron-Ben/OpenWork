复盘刚修好的 bug，结果用中文。目的不是解释这一个 bug，而是让同一类问题不再出现。

## 1. 回答三个问题

**根因属于哪一类**（选一个，写出具体原因）：

| 类别 | 特征 | 本项目的例子 |
|---|---|---|
| 没写规范 | 该怎么做从没写下来 | 工作区文件名大小写不敏感没有写进规则 |
| 层间约定不清 | 两层对同一数据理解不同 | token 估算把不发给模型的 artifact 也算进去 |
| 改了一处漏了别处 | 同一概念有多个副本 | 暂无实例；潜在风险是路径规则的两份实现（文件工具判断与 Seatbelt 规则）|
| 测试没覆盖 | 单独能过，组合起来就坏 | 保留期测试被其他测试的旧时间戳干扰 |
| 隐含假设 | 代码依赖没写明的前提 | 以为拒绝信息一定是 "Operation not permitted" 大写开头 |

**同类问题还可能出现在哪**：实际去搜，给出 grep 命令和命中位置；没有搜到就写搜了什么。

**能不能从结构上防住**：按由强到弱选能用的最强手段：

1. 类型或结构让错误写不出来；
2. 测试覆盖这一类输入（例如对等测试、大小写变体）；
3. 可执行的 grep 检查；
4. 写进规则文件，靠审查发现。

只能做到第 4 条时，说明为什么前三条做不到。

## 2. 把结论落到文件里

复盘只留在聊天里等于没做。按内容选位置：

- **行为本身有误或文档没写清**：改 `docs/` 下对应的设计文档。这会改变设计，先停下来问用户。
- **写代码时的约定**：写进 `.claude/rules/<主题>.md`，已有同主题文件就追加。照 `.claude/rules/database.md` 的写法：
  - 一句话规则；
  - 正误对照（`✅` / `❌` 代码片段）；
  - 能运行的检查命令，写明期望输出。
- **能加的测试或检查**：直接加上；超出本次范围的，写进进度文件的待定项。

新建规则文件时，在开头注明适用范围（哪些目录或模块）。每个文件控制在 100 行以内，超过就按主题拆分。

## 输出

```text
Bug：<一句话>

根因：<类别> — <具体原因>
同类位置：<grep 命令> → <命中位置，或"无">
防护：<手段>（<为什么选它>）

已修改：
- .claude/rules/xxx.md：<新增的规则>
- <测试文件>：<新增的测试>
需要决定：<要改设计文档的地方；没有就写"无">
```
