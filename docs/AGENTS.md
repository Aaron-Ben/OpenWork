# 文档标准

本文规定文档分层与写作规则。`docs/CLAUDE.md` 是指向本文的软链接。Agent Note 的格式见 [.agents/notes/README.md](../.agents/notes/README.md)。

这里的“文档”指仓库里的 Markdown 文件，不包括两类：测试快照（`__snapshots__/` 下由测试生成的模型提示词），以及描述 Rust 版、不再修改的文档（`crates/`、`desktop/`、`.agents/notes/legacy/` 与两个旧子系统页）。

## 1. 一个事实只有一个位置

每个事实只写在负责它的那一层。其他位置只写链接。

| 层 | 放什么 | 不放什么 |
|---|---|---|
| 根 [AGENTS.md](../AGENTS.md) | 每个会话都需要的常驻规则。每条一到三行，并链接负责的文件；不显然的规则带半句理由 | 例子、操作步骤、从其他文件复制的内容 |
| [packages/AGENTS.md](../packages/AGENTS.md) | `packages/` 与 `apps/` 的代码约定 | 文档规则 |
| 本文 | 文档标准 | 代码约定 |
| 根目录 [README.md](../README.md) 与 `README.en.md` | 给第一次看到项目的人：能做什么、架构概要、怎样运行。两份内容保持一致 | 规则、子系统的细节与数字 |
| [docs/README.md](README.md) | 文档索引与阅读顺序 | 规则 |
| [architecture.md](architecture.md) | 进程、包、依赖方向、数据归属与领域词汇 | 单个子系统的细节、决策理由 |
| [testing.md](testing.md) | 测试分层、原则、写法与运行方式 | 单个子系统的验收条目 |
| [defensive-patterns.md](defensive-patterns.md) | 本仓库实际出现过的缺陷：现象、规则、出处 | 没有发生过的假想问题 |
| `.agents/tasks/<任务>.md` | 分多块的长任务：每块的完成标准与进度 | 决策理由、规则 |
| `.agents/skills/<名字>/SKILL.md` | 在某个时刻照着做的流程，例如提交。规则只链接，不复述 | 常驻规则、测试与写法的规则、子系统的事实 |
| `docs/subsystems/<子系统>.md` | 一个子系统已实现的行为、数据结构、数字、边界与验收清单 | 决策理由、备选方案、目标状态、迁移叙事 |
| [Agent Notes](../.agents/notes/README.md) | 决策理由、放弃的方案、代价；还没实现的设计（`proposed/`） | 当前行为的完整规则、数字与默认值 |
| 包 README | `packages/` 与 `apps/` 下每个包一份，按[模板](templates/package-readme.md)写：入口、源码地图、对模型上下文的影响、已知限制 | 子系统页已有的行为与数字 |
| 代码注释 | 这段代码为什么这样写 | 复述代码，复述设计文档 |

## 2. 子系统页

- 一个子系统写一页，放在 `docs/subsystems/`。子系统按功能划分，可以跨多个包。
- 只写已经实现的事实：行为、类型、数字、清单与边界。不写理由，在相关小节末尾链接负责的 Agent Note。
- 不写目标状态与“尚未实施”。不写迁移叙事，“以前是什么样”属于 git 历史。
- 页末是“验收”一节。每条写出覆盖它的测试；没有自动测试时，写“手动”，并说明怎样验证。

## 3. 写作规则

- 文档用中文。例外是 `README.en.md`，以及模型可见的文本：给 Agent 的提示词用英文。
- 用短句。一句只写一件事，指令用祈使句。
- 用主动语态，写清楚谁做什么。
- 一段只讲一个主题。规则多时拆成列表。
- 项目专有名词（Room、Agent、Engine、Run 等）保持原样。
- 行内代码里写本仓库的路径时，从仓库根目录写起，例如 `apps/desktop/electron/main.ts`。引用参考项目的文件写成 `项目:路径`，例如 `raft:packages/cli/src/main.ts`。`pnpm lint` 检查这两类路径都存在。
- 还没建的文件，以及构建产物等不在 git 中的路径，不写成以仓库目录开头的行内代码：本机有这些文件时检查能通过，新克隆的仓库上会失败。
- 只给改变行为的那一句加粗。处处加粗等于没有重点。

## 4. 低质量写法清单

审查文档时，查找这些写法：

- 同一条规则写在多处。搜索一句有特征的原文，只保留一处，其他位置改为链接。
- 在不该写历史的层写历史。改为写当前事实，并链接历史所在的位置。
- 状态标注，例如“已实现！”“以后再做：…”。
- 复述代码、生成结果或测试清单。只列文件名、不写各自负责什么的文件清单也算；包 README 的源码地图写了职责，不算。
- 推理过程：逐步叙述实现、证明显而易见的分支、复述测试过程。保留结论，删去推导。
- 段落墙：一段里塞进多条规则和括号说明。拆开，或把细节移到负责的位置。
