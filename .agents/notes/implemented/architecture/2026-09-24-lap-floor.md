# Agent Note: Agent 之间的讨论满一轮即停（lap floor）

Status: implemented

## 问题

Agent 之间的对话没有自然的终点。每个 Agent 醒来都重新判断要不要说，没有全局的停止信号。实现点名路由后的实测中，三个 Agent 回答了一个开放问题后，又各接了一轮，因为 triage 模型把同伴的消息判为 actionable。原有的 20 条硬上限来得太晚。

需要一个不调用模型、随参与人数伸缩的停止点。同时，用户旁观时，Agent 之间的活动不应一轮就停。

## 决策

- `agent_loop_verdict`（`crates/openwork-collab/src/server/triage.rs`）的判断顺序是：20 条硬上限（`AGENT_LOOP_HARD_CAP`），私聊检查点（每 8 条），lap floor。每个未读房间都满足 `agent_streak > agent_authors` 时，以 `lap_floor` 跳过，不调用模型。
- `InboxTriage::context` 的 SQL 算出这两个数：最近一次人类关注之后的 Agent 消息数 `n`，与发这些消息的不同 Agent 数 `k`。人类关注取两者中较大的 sequence：最后一条非 Agent 消息，与 `collab_rooms.user_viewed_seq`。
- Desktop 上报用户看到的位置，`Rooms::mark_viewed`（`server/rooms.rs`）记录它，只增不减。迁移是 `202609240004_user_viewed_seq.sql`。
- lap floor 只在 triage 时判断。`reply` / `dm` 写入时只检查 20 条硬上限（`Messages::agent_loop_capped_in`，拒绝码 `LOOP_CAP`）。

规则见 [collaboration.md §8.3、§13.3.4](../../../../docs/subsystems/collaboration.md)。

## 考虑过的方案

**Cumora 的认领档。** Cumora `pastFloor`（`server/src/agents/triage-core.ts`）对有 worklog 认领的房间把上限放宽到 20。不采用：Cumora 的 `cmdClaim`（`cli.ts`）已不再写房间范围的认领，这一档是死代码。

**Cumora 的全租户在场档。** 人类在 10 分钟内读过租户内任何房间时，所有房间放宽到 20（`runtime/inproc-client.ts` 的 `humanRecentlyActive`）。不采用：范围过粗。

**用时间戳记录用户查看（`user_viewed_at`）。** 讨论时说的是时间戳。Cumora 也用读取时间与消息的 `created_at` 比较（`triage-core.ts` 的 `agentRunByConvo`）。改为 sequence：按 sequence 判断用户看过哪些消息，没有时钟问题，同一个值还能直接算未读。

**写入时也判断 lap floor。** 没有采用，只在 triage 时判断。Cumora 也这样：`cli.ts` 的 `reply` 没有 lap 检查。

**去掉 20 条硬上限。** 不采用。Cumora 的注释记录它删过两次，每次都回归（`triage-core.ts` 的 `HARD_LOOP_CAP`）。

## 后果

- 讨论在一整轮后停下。阈值随人数变化，判断不花 token。
- 多个 Agent 同时基于 n = k 的状态醒来时，都会通过 triage，最多多出一轮并发接话。实现 lap floor 后的实测：三人同时各接一句，之后的唤醒以 `lap_floor` 跳过。
- 两人私聊在第 8 条检查点也会以 `lap_floor` 跳过，因为 8 条只来自 2 个 Agent。
- 用户看着房间时，看过的 Agent 消息不计入 `n`，讨论能继续。用户离开后，下一轮结束时停下。
- `user_viewed_seq` 放在房间上，不放在成员表上，因为用户能查看自己不是成员的 Agent 私聊。Desktop 的未读数也用它（`server/room_summaries.rs`）。
- 写入时的闸见 [发布前的三道闸](2026-09-24-reply-gates.md)。
