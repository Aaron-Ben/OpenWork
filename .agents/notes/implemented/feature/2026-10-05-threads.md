# Agent Note: 讨论串（第 5a 步）

Status: implemented

## 问题

群聊只有一条时间线。几件事同时讨论时，回复互相穿插，用户和 Agent 都要自己分辨哪句接哪句。用户在群里的每条消息还会唤醒全部 Agent 成员，只跟一两个 Agent 有关的细节讨论也让其余 Agent 白跑。

第 5b 步的任务也需要一个地方放“这个任务的讨论与状态通知”，见 [任务 Note](2026-10-05-tasks.md)。2026-10-05 用户决定做讨论串，第 5 步拆成 5a 讨论串与 5b 任务，讨论串先做（[路线图](../../proposed/architecture/2026-10-04-typescript-rewrite.md)“实现顺序”第 5 步）。用户要求把讨论串和普通聊天区分清楚，重点讨论三件事：Agent 拿到什么信息、要不要按讨论串开不同的会话；Agent 在哪里回复；表怎样设计。

### 参考项目的做法

2026-10-05 读源码确认。

**raft 有完整的讨论串：**

- **讨论串是一行独立的频道。** `channels.type = 'thread'`，用 `parent_message_id` 指向宿主消息，每条消息最多一个讨论串。讨论串里的回复就是这个频道里的普通消息，所以已读位置、HELD 和收件箱都直接复用（`raft:packages/server/src/db/schema.ts`）。讨论串没有自己的成员行，谁能发言看父频道的成员。
- **只通知关注者。** 讨论串里的消息只发给它的关注者，不发给父频道的全部成员。以下几种人自动关注：在讨论串里发过言的人、宿主消息的作者、在讨论串里被 @ 到的父频道成员。Agent 只能取消关注（`raft:packages/server/src/services/messageService.ts`）。
- **Agent 看到的信息。** 讨论串在 Agent 的收件箱里是单独的一组。只有被 @ 进讨论串时，才附上宿主消息和最近 6 条回复（`THREAD_JOIN_CONTEXT_WINDOW`）；平时只给新消息（`raft:packages/daemon/src/agentRuntimeInput.ts`）。
- **在哪里回复。** 常驻规则写着：在消息来的地方回复；把某条消息的 ID 当作地址发言，就在这条消息下开出讨论串；讨论串不能嵌套（`raft:packages/daemon/src/drivers/raftCliGuide.ts`，`buildThreadsSection`）。Agent 读过某个讨论串后又往父频道发言，命令会先拦下来要求确认（`raft:packages/cli/src/commands/message/send.ts`，`detectThreadContextParentSend`）。
- **任务。** 任务的状态通知只发到任务的讨论串（`raft:packages/server/src/routes/tasks.ts`，`postTaskLifecycleToThread`）。

**cumora 与旧版 OpenWork 没有讨论串，只有引用回复：** 消息上有一个可空的 `quoted_message_id`，回复仍在同一条时间线上（`cumora:server/src/db/migrate.ts`；`git show dd8779b:crates/openwork-collab/migrations/202609240002_message_quotes.sql`，旧版代码已在第 9 步删除）。cumora 在界面上加了一个侧栏，把引用同一条消息的回复集中显示（`cumora:src/desktop/ThreadDrawer.tsx`）。

**三个项目都是每个 Agent 只有一个 Engine 会话**，跨房间、跨讨论串共用（`raft:packages/daemon/src/agentProcessManager.ts`；`cumora:server/src/agents/computer/session-store.ts`；Crew 的 `packages/computer/src/home.ts` `SessionKey`）。

## 决策

2026-10-05 讨论，用户逐项同意；实现时与讨论有两处出入，见各条的“实现时”。

**数据：讨论串是一个房间。** `rooms.kind` 增加 `thread`，加 `parent_room_id` 与 `parent_message_id`（唯一，每条消息最多一个讨论串），迁移 `0004_threads.sql`。讨论串里的回复是这个房间的普通消息，序号、`postMessage`、HELD、Agent 与用户的已读位置、收件箱、运行记录的唤醒来源都不用改。讨论串没有成员行，谁能发言、@ 谁算数看所在群聊的成员。回复数就是讨论串房间的 `next_seq`。讨论串里不能再开讨论串。

- 实现时：关注者没有另建 `thread_followers` 表。关注一个讨论串就是在它里面有一行 Agent 已读位置：收件箱本来就按已读位置取消息，关注者因此自动收到讨论串的消息；另建表时，两张表要一直保持一致。关注的原因（作者、发过言、被 @）没有存，现在没有地方用到。
  - 2026-10-05 用户问：一个 Agent 关注多个讨论串会不会出问题。不会：已读位置的主键是（Agent，房间），每个讨论串是一个房间，各有一行，互不影响；收件箱按房间分组，同一轮里每个讨论串各成一段；确认已读时各行一起推进。真正受影响的是“取消关注”：现在不能取消，Agent 关注过的讨论串，之后用户在里面的每条消息都会唤醒它。要做取消关注时，在已读位置上加一列标记，或者到那时再建关注表；直接删掉那一行不行，再关注时已读位置会回到 0，把整个讨论串重读一遍。

**唤醒。** 讨论串里用户的消息唤醒全部关注者，不唤醒群里的其他 Agent；还没有 Agent 关注时，群里的 Agent 全部关注并被唤醒，免得没人回答。Agent 的消息与群聊一样只唤醒它 @ 到的其他成员。关注者是宿主消息的作者（是 Agent 时）、在讨论串里发过言的、被 @ 到的 Agent（`packages/server/src/messages.ts` 的 `threadWakeTargets`）。第 5b 步加上任务的负责人。

**Agent 拿到的信息。** 讨论串在本轮输入里单独成段，写出所在群聊的名字与成员，并附上宿主消息（正文至多 600 字符）。跟 raft 不同，宿主消息每次都附上：Crew 一轮输入里只有未读消息，没有宿主消息时 Agent 不知道讨论串在讨论什么。新关注者的已读位置从 0 开始，第一次被唤醒时读到讨论串里已有的回复；它第一次在讨论串里发言前，HELD 会先给它看这些回复。

**会话：仍然每个 Agent 一个会话。** 理由：一个 Agent 的工作目录只有一个、Runner 串行跑，分开的会话要么互相等、要么同时改同一个目录；分开的会话互不知情，Agent 在讨论串 A 答应的事在讨论串 B 里会忘掉；每多一个会话就多一次缓存未命中。会话太长时用第 6 步的记忆压缩。

**在哪里回复。** 讨论串的地址是它自己的房间 ID，`crew reply <thread-id>` 不用改；开讨论串用 `crew reply <room-id> --thread <message-id>`，不另做 `crew thread` 命令。常驻规则写：在消息来的地方回复；只在用户要求时开讨论串。不做 raft 那种“读过讨论串后往父房间发言要先确认”，先观察真实演示。

- 实现时：`--thread` 接消息 ID，不是讨论时说的序号。Agent 在本轮输入里看到的是 `[消息 ID]`，看不到序号。

**私聊不开讨论串。** 用户决定：一对一的私聊没有讨论串，只有群聊能开。

**界面。** 用户要求界面更现代，右侧那一栏要能整栏放大，确认了设计稿 `apps/desktop/out/mockups/step5-threads-tasks.html`（不在 git 中）：

- 右栏由运行记录、讨论串与任务共用，同时只显示一个（`apps/desktop/src/components/SidePanel.tsx`）。栏头可以放大整栏：放大后右栏占去聊天区与右栏两栏，聊天区让出来，视图切换搬到栏头（2026-10-05 用户要求，设计稿 `apps/desktop/out/mockups/step5-layout.html`；最初的做法是把聊天挤成 340px 的窄列，另有“专注”收起会话栏，已删除）。
- 右栏是一张浮在页面上的卡片：四周留白、圆角、阴影，卡片内没有分隔线。聊天顶栏没有横线，与消息区同底色，消息滚过顶部时下沿出现一道渐隐；右栏打开时顶栏只留头像、名字、状态与视图切换。侧栏去掉竖线，靠底色区分（2026-10-05 用户选方案 A，设计稿 `apps/desktop/out/mockups/step5-cards.html`）。
- 侧栏顶部没有大标题：第一行右边是“隐藏侧栏”，第二行是“＋ 新建”与连接状态；侧栏收起后，聊天顶栏或放大的右栏栏头最左边是“显示侧栏”，⌘\ 切换（2026-10-05 用户选方案 A）。
- 讨论串的消息不进群聊时间线；宿主消息下显示参与者、回复数、最后回复时间与新回复数，点击在右栏打开；鼠标移到群聊消息上出现“开讨论串”“复制”。
- 运行记录放大后分左右两栏：左边是轮次，右边是选中那一轮的时间线。
- 会话列表里，群聊的未读数包含它的讨论串的未读，最后活动也算上讨论串里的消息。
- Agent 在讨论串里回复时，它在群聊顶栏与会话列表里的状态是“回复中”，但实时活动框只出现在讨论串里，不出现在群聊时间线上（2026-10-05 用户决定）。活动框按这一轮的唤醒来源判断（`MessageParts.tsx` 的 `LiveActivity`）。

## 考虑过的方案

- **cumora 式的引用回复（只加 `quoted_message_id`）。** 实现最少，但回复仍在主时间线上，不能把讨论和主聊天分开，也不能缩小唤醒范围，达不到用户“区分清楚”的要求。
- **在 `messages` 上加 `thread_root_id`，讨论串的消息与房间共用序号。** 已读位置、HELD 都按房间算，要给每处加上“是不是讨论串”的分支；讨论串做成房间时这些全部复用。
- **每个讨论串一个 Engine 会话。** 见“会话”一条。
- **另建 `thread_followers` 表。** 见“数据”一条的“实现时”。

## 验收条件

- 讨论串的开出与复用、唤醒与关注、一个 Agent 关注多个讨论串、拒绝私聊与嵌套、收件箱内容、新关注者的 HELD、未读与运行记录：`packages/server/test/api.test.ts` 的 `threads`。
- `crew reply --thread` 与它的输出：`packages/computer/test/shim.test.ts`；本轮输入与常驻规则的文本：`turn-prompt.md`、`AGENTS.md` 快照。
- 真实模型演示（2026-10-05，`deepseek/deepseek-flash`）：用户在群里 @alice 提问，Alice 与 Bob 都被唤醒，Bob 白跑；用户在那条消息的讨论串里 @alice，只有 Alice 被唤醒并在讨论串里回复，群聊时间线上只多了讨论串摘要。

## 风险

- Agent 可能在主房间回复讨论串里的问题，或者反过来。规则写清楚后，用真实演示观察。
- 只唤醒关注者后，没关注的 Agent 不再看到讨论串里的内容。需要它参与时，用户或别的 Agent 要 @ 它。
- 成员变化：现在只能加成员。以后支持移出成员时，要同时删掉它在这个群全部讨论串里的已读位置，raft 为此专门写了 `purgeAgentInboxForChannelTree`。
- 讨论串唤醒的一轮失败时，“上一轮没有完成”的提示出现在群聊时间线上，不在讨论串里：出错的状态只带房间，不带是哪一轮，界面分不出来。
