# Agent Note: 任务（第 5b 步）

Status: implemented

## 问题

群里说“这几件事分一下”之后，事情只存在于聊天记录里：谁接了、做到哪了、做完没有，都要翻消息才知道。Agent 也没有办法声明“这件我来做”，两个 Agent 可能同时去做同一件事。

路线图见 [重写的路线图](../../proposed/architecture/2026-10-04-typescript-rewrite.md)“实现顺序”第 5 步，已经定下的形状：房间里的消息可以转成任务；状态固定为待办、进行中、待审、完成、关闭，按状态显示成看板或列表；Agent 领取任务是一次 compare-and-swap；分配任务时发一条系统消息并 @ 对方，复用第 3 步的唤醒与 HELD，不另做卡片唤醒。

### raft 的做法

2026-10-05 读源码确认：

- 表 `tasks` 挂在频道上，编号在频道内递增，状态固定为 `todo`、`in_progress`、`in_review`、`done`、`closed`，只有一个负责人，`message_id` 指向宿主消息。每次修改把 `revision` 加一，用来做乐观并发。另有 `task_events` 记下每次状态与负责人的变化（`raft:packages/server/src/db/schema.ts`）。
- 状态流转有一张允许表，比如 `todo` 只能去 `in_progress` 或 `closed`。改状态不限于负责人，频道成员都能改，注释里写着理由：限制只给负责人时，任何人都能先把任务分给自己再改，限制什么也没挡住（`raft:packages/server/src/services/taskService.ts`，`VALID_TRANSITIONS` 与 `writeCanonicalStatus`）。
- “领取”与“分配”是两个动词。领取表示“我开始做了”，一次带条件的 UPDATE，把负责人设成自己、把 `todo` 推进到 `in_progress`，失败时说明原因，比如已被别人领取。分配只换负责人，不改状态（同一文件，`writeCanonicalClaim` 与 `assignTask`）。
- 创建时直接分配，会在同一个事务里写一条 “📌 Assigned @x to task #N” 的系统消息，并给负责人记一条 @，复用普通的未读与唤醒（同一文件，`createTasksWithAssignmentReceipt`）。其余领取、分配、改状态的通知发到任务自己的讨论串，不发到频道：用户要求频道保持干净（`raft:packages/server/src/routes/tasks.ts`，`postTaskLifecycleToThread`）。
- 界面在看板与列表之间切换（`raft:packages/web/src/components/task/TasksPanel.tsx`）。Agent 用 `raft task create`、`claim`、`update`、`assign` 等命令（`raft:packages/cli/src/commands/task/`）。
- Agent 怎样看到任务（`raft:packages/daemon/src/drivers/raftCliGuide.ts`，Tasks 一节）：任务就是一条带任务信息的消息，`task create` 等于“发一条新消息，再把它变成任务”；Agent 读到的宿主消息后面带 `[task #3 status=in_progress]` 后缀；规则写着“要动手做事（跑工具、改文件）之前先 claim，只是回答问题不用”，进展发在任务的讨论串里，做完改成 `in_review` 等人确认；讨论串里的消息不能转成任务。

raft 为多用户、多服务器和外部资源回执付出了大量复杂度。外部资源回执是给“会在外部建资源的任务”（比如开一台云服务器）准备的：改成完成之前必须填写建了什么、谁负责回收、何时过期等，数据库用检查约束强制（`raft:packages/server/src/db/schema.ts`，`tasks_resource_receipt_*`）。2026-10-05 用户决定外部资源回执先不做：Crew 的 Agent 只在本机沙箱目录里工作。

下面的推荐取 raft 的四样：固定状态、带条件的领取、用系统消息加 @ 唤醒负责人、状态通知发到任务的讨论串。讨论串见 [讨论串 Note](2026-10-05-threads.md)，2026-10-05 用户决定做。

## 决策

2026-10-05 第 5a 步讨论串做完后重新整理。2026-10-05 用户同意下面全部推荐，也同意先不加“在群里新建任务”的快捷方式。界面的样子已经在设计稿 `apps/desktop/out/mockups/step5-threads-tasks.html` 里确认过（任务列表、看板、任务详情、下拉菜单），这里只列还没定的。

1. **数据。** 一张 `tasks` 表：`room_id`、房间内递增的 `number`、`title`、`status`、`assignee_agent_id`（可空，只能是 Agent）、创建者（用户或 Agent）、`message_id`（宿主消息，**必填**，每条消息最多一个任务）、`claimed_at`、`completed_at`、时间戳。不加 `revision` 与 `task_events`（理由见“考虑过的方案”）。宿主消息必填：照 raft，“新建任务”就是以创建者的身份发一条正文为标题的普通消息，再把它变成任务；这样每个任务都有宿主消息和讨论串，不用处理“没有宿主消息的任务”。讨论串里的消息不能转成任务。
2. **系统消息。** 通知（转成任务、分配、领取、改状态）是一种新的消息：`messages` 加一列 `kind`（`text` 或 `system`），作者列照旧记下是谁的操作。这样不用改“恰好一个作者”的约束，而且 HELD 自然不拦自己的操作（Alice 领取后再回复，不会被“Alice 领取了 #3”拦下），用户的未读也不算自己的操作。系统消息只唤醒它 @ 到的 Agent，不管作者是谁。界面显示成一行灰字。群聊里发到任务的讨论串；私聊没有讨论串，发到私聊的时间线。
3. **什么时候 @ 负责人（会唤醒它）。** 只在两种时候：分配给它；别人把它的任务退回（待审或完成退回到进行中或待办）。领取、改成待审、完成、关闭都不 @ 任何人：用户在界面上能看到，Agent 不需要为此跑一轮。负责人同时成为讨论串的关注者。
4. **权限与流转。** 用户什么都能做。Agent 能创建、领取、改状态、分配给别的 Agent。照 raft，不限制只有负责人能改状态。流转用 raft 的允许表。分配只换负责人，任务留在待办；领取把负责人设成自己并推进到进行中，用带条件的 UPDATE，失败时说明原因。
5. **`crew task` 命令。** `crew task create <room-id> <title> [--assign <handle>]`、`crew task convert <room-id> <message-id> [--assign <handle>]`（把已有消息转成任务，标题取正文第一行）、`crew task list <room-id>`、`crew task claim <room-id> <number>`、`crew task status <room-id> <number> <status>`、`crew task assign <room-id> <number> <handle>`。房间 ID 放在第一个参数，与 `crew reply` 一致；输出用英文，写出任务的讨论串 ID，方便接着在讨论串里汇报。领取不做 HELD：条件 UPDATE 已经防住了重复领取。
6. **Agent 怎样看到任务。** 照 raft：本轮输入里，宿主消息后面加 `[task #3 in_progress, assigned to @alice]`；讨论串段的标题也写上它是哪个任务。不另加“你的任务清单”一段：被分配时会被唤醒，进展在讨论串里，需要全貌时用 `crew task list`。
7. **Agent 的规则。** 常驻规则加一节：要动手做事之前先领取，只是回答问题不用；被分配后先领取再做；进展发在任务的讨论串里；做完改成待审，等用户确认；不要把同一件事建成两个任务，建之前先 `crew task list`。
8. **界面里的入口。** 鼠标工具条加“转为任务”；任务面板顶部“新建任务”是一行输入框（标题加可选的负责人），回车创建；宿主消息下显示任务标签（状态图标、编号、状态、负责人），点击打开任务详情。任务详情就是任务的讨论串，上面多一栏状态与负责人的下拉菜单。看板放不下五列，选“看板”时右栏自动放大（设计稿已定）。

### 实现时

- **带条件的更新。** 领取、改状态、换负责人都是带条件的 `UPDATE … RETURNING`：领取要求待办并且没有负责人或负责人是自己，改状态要求状态仍是读到的那个，换负责人要求状态与负责人都没变；没更新到时读出现在的样子说明原因（`packages/server/src/tasks.ts`）。数据库另有约束：进行中与待审一定有负责人。
- **写消息拆成两层。** `postMessage` 自己开事务；任务操作用 `postMessageIn` 在自己的事务里写标题消息与通知。新建任务的标题消息是操作的一部分，不做 HELD 检查（`action`）；分配了负责人时它不唤醒任何 Agent（`quiet`），由通知唤醒负责人。
- **通知的文字。** 新建与转换都写一条通知（“新建了任务 #3”“把这条消息转成任务 #3”，分配时加“，分配给 @alice”），群聊里因此在创建时就开出任务的讨论串。
- **拒绝原因。** Server 拒绝时返回 `{ error, refusal }`，`refusal` 是 protocol 的 `TaskRefusal`；界面显示中文 `error`，`crew` 按 `refusal` 写英文说明与下一步。
- **看板。** 选“看板”时右栏放大并收起会话栏：在 1100px 宽的窗口里，只放大右栏时看板只有 520px，放不下五列。还原时切回列表。这一点比设计稿多收起了会话栏。
- **Agent 的规则。** 不是任务的请求要动手时，用 `crew task convert` 把提出请求的那条消息转成任务再领取，不另发一条标题消息。

## 考虑过的方案

2026-10-05 用户问为什么不加 `revision` 与 `task_events`、为什么只做一张表、为什么系统消息与任务改动写在同一个事务里，下面是当时的回答。

- **`revision` 版本号（raft 的乐观并发）。** raft 有多个用户在网页上编辑同一个任务，客户端带着读到的版本号提交，版本变了就拒绝，让客户端重读再试（`raft:packages/server/src/routes/tasks.ts`，分配接口返回 `currentRevision`）。Crew 只有一个用户，Agent 用命令表达意图（“领取 #3”“#3 改成待审”），不是在旧画面上提交表单。每次写入都把它依赖的字段放进条件里就能防住并发：领取要求 `status = 'todo' AND assignee IS NULL`，改状态要求状态仍是读到的那个。以后加了多方编辑标题、描述的功能，再加版本号。
- **`task_events` 事件表。** raft 的状态通知在任务改动提交之后才发，失败了也只记日志、不回滚（`raft:packages/server/src/routes/tasks.ts`，`postTaskLifecycleToThread` 的注释），通知会丢，所以要另一张表可靠地记历史。Crew 把系统消息和任务改动写在同一个事务里，消息不会丢，房间里的系统消息就是历史，用户和 Agent 看到的是同一份。再加事件表，同一份历史就存了两处。
- **系统消息与任务改动写在同一个事务里。** 分配通知带着对负责人的 @，Agent 是被这条消息唤醒的。分开写时，任务改了、通知没写成（进程退出、数据库断开），负责人就永远不会被唤醒，讨论串里的历史也缺一段；反过来先写通知、任务没改成，历史里就记了一件没发生的事。写在一个事务里，两者要么都成、要么都不成。代价是通知写失败时任务也改不成；两者在同一个数据库里，这种失败本来就意味着任务也写不进去。raft 在任务提交后才发通知，因为它的讨论串可能要临时创建、还要跨服务器投递，失败时宁可丢通知也不挡任务；Crew 在创建任务时就开好讨论串，没有这个顾虑。
- **为什么只有一张表，而第 4 步有 `runs` 与 `run_events` 两张。** 运行事件一轮几十条，只在运行记录面板里看，不进聊天，所以单独成表。一个任务一生只变几次（创建、分配、领取、待审、完成），每次变化本来就要写一条系统消息到它的讨论串里，这些消息已经是完整的历史，不需要第二张表。只做一张表的代价是：以后要做“任务时间线”或“从领取到完成用了多久”这类统计时，要从系统消息里查。`tasks` 上的 `claimed_at`、`completed_at` 先覆盖最常用的时长统计。

- **讨论串里的消息为什么不能转成任务。** 2026-10-05 用户问。每个任务的通知与讨论放在它宿主消息的讨论串里；宿主消息在讨论串里时，它的讨论串就是讨论串里的讨论串，第 5a 步已经定了不嵌套。另外两条路都更糟：任务没有自己的讨论串、通知发进它所在的讨论串，几个任务的通知就混在同一个讨论串里；任务藏在讨论串里，群聊时间线上看不到它的标签，只能在任务面板里找到。raft 同样拒绝（`raft:packages/server/src/routes/tasks.ts`，领取讨论串里的消息返回 409），规则写着讨论串里的消息是讨论的上下文，任务只从顶层消息来（`raft:packages/daemon/src/drivers/raftCliGuide.ts`）。讨论串里聊出一件要做的事时，用“新建任务”在群里发一条新消息，用户决定先不在讨论串消息的菜单里加“在群里新建任务”的快捷方式，真实使用中发现常用再加。
- **系统消息为什么是 `messages.kind`，不是新的“系统”作者。** 2026-10-05 用户问。“Alice 领取了 #3”这条通知是 Alice 的操作引起的。作者写成“系统”（两个作者列都空）时，Server 不知道是谁做的：Alice 领取后接着回复，HELD 把这条通知当成“别人发的新消息”拦下她自己的回复；用户自己点了“完成”，这条通知又算进用户的未读。作者照旧写成做这件事的人，另用 `kind = 'system'` 标出“这是通知，不是聊天”：HELD、未读、唤醒都按作者算，结果都对；界面按 `kind` 把它画成一行灰字；Agent 的本轮输入里标成通知。raft 的做法类似：通知带着引起它的人（`causalActor`），这个人不把它算作未读（`raft:packages/server/src/routes/tasks.ts`，`postTaskLifecycleToThread`）。

## 验收条件

- 新建、转换、领取、改状态、换负责人与各种拒绝，两个 Agent 同时领取只有一个成功，只在分配与退回时唤醒负责人，Agent 不被自己的通知拦下，用户不把自己的通知算作未读：`packages/server/test/api.test.ts` 的 `tasks`。
- `crew task` 的输出：`packages/computer/test/__snapshots__/shim-output.md`；本轮输入里的任务后缀与通知标记：`turn-prompt.md`；常驻规则：`AGENTS.md`。
- 真实模型演示（2026-10-05，`deepseek/deepseek-flash`）：用户把“写 reset-password.md”的消息转成任务并分配给 @alice；Alice 领取、写好文件、改成待审并在任务的讨论串里汇报；用户改成完成。截图核对了任务标签、列表、看板与任务详情。

## 风险

- 状态通知发到讨论串后，只有讨论串的关注者会读到，主房间不受影响；但负责人每次被分配都会被唤醒，频繁改派时它会多跑几轮。
- Agent 可能不领取就动手，或者做完忘了改成待审。规则写清楚后，用真实演示观察；需要时在 `crew reply` 的输出里提醒。
- 用户新建的未分配任务照普通消息唤醒群里全部 Agent。演示里 Alice 在同一轮里顺手领取并做完了它，Bob 白跑了一轮。需要时可以让未分配的新任务不唤醒任何 Agent，只在任务面板里等人领取。
