# Agent Note: triage（第 7 步）

Status: proposed

## 问题

群里用户的每条消息都唤醒全部 Agent 成员，每个 Agent 跑一整轮：启动 OpenCode，把常驻规则、工具说明与未读消息交给主模型。没轮到自己的 Agent 读完后沉默，这一轮就是白跑。2026-10-05 的真实演示里，用户 `@alice` 提问，Bob 也被唤醒，两轮都白跑，每轮约 8.5k token。

路线图见 [重写的路线图](../../proposed/architecture/2026-10-04-typescript-rewrite.md)“实现顺序”第 7 步：先用运行记录量出白跑，再用一次便宜的模型调用提前判断，用评测集衡量省下的与漏掉的。

## 提议

2026-10-05 读源码确认的事实，它们改变了“对每条消息做 triage”的原计划：

- cumora 不对用户在群里的消息做 triage：用户消息一律参与，注释写着 “human message in group — always engage, no triage gate”（`cumora:server/src/agents/triage-core.ts`）。triage 只判断 Agent 之间的消息；判断失败时，批次里有人类消息就 fail open。
- Rust 版 OpenWork 同样让人类消息确定性参与（旧版文档已在第 9 步删除，原文见 `git show dd8779b:docs/subsystems/collaboration.md` §8.3 第 2 步）。唯一的例外是**用户点名了别的 Agent**：没被点名的 Agent 先回答一道路由题，“这条是给被点名的人，还是给整个房间”，答 `me` 才跳过，出错或答不清都按参与处理（§8.2；那份 Note 已在第 9 步删除，原文见 `git show dd8779b:.agents/notes/legacy/architecture/2026-09-24-per-agent-triage-for-unaddressed-messages.md`）。题面照搬 cumora 的 `routing.ts`。旧版实测：`@bo` 提问时，另外两个 Agent 答 `me`，不跑主模型，只有 Bo 回复。
- Crew 第 3 步已经让 Agent 的消息只唤醒它 @ 到的成员，所以参考项目里 triage 主要处理的那类消息（Agent 之间的闲聊）在 Crew 里本来就不会唤醒别人。Crew 的白跑只来自用户在群里的消息。

2026-10-05 用户决定 triage 先不做，先做任务与提醒；下面的决策点留到那时再讨论。

### 待定的决策点

1. 白跑统计：量什么、在哪里看。
2. 判断哪些消息。
3. 在哪里判断、用什么模型。
4. 判断失败怎么办。
5. 跳过的消息算不算已读，Agent 以后怎样看到它们。
6. 跳过怎样记进运行记录。
7. 评测集的形式与标注。
